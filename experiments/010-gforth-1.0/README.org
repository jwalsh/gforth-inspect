#+TITLE: 010 gforth-1.0: v0.1.1 against gforth 1.0.0 and 1.0.1
#+DATE: 2026-11-22
#+STARTUP: showall

A compatibility finding, not a port.  The project supports gforth 0.7.3
only (CONTRIBUTING.org, "gforth 0.7.3 only"); this experiment says what
happens when a user loads the released inspector into gforth 1.0 anyway.
Nothing under =env/= or =contract/= changes here.  The load-time notice
for a non-0.7.3 gforth belongs to v0.2.0, not to this branch.

* Hypothesis

v0.1.1 (=env/inspect.fs= blob =82860519a7d3=) loads on gforth 1.0.x, and
the log it writes there is valid against contract 1.1 and begins with
={"v":1,= (I-1, D-38), but =dbg-fix= / =dbg+= and the return-stack words
(=.rs=, =rs-full=, the =rs= field) fail, because they walk 0.7.3's
threaded code, headers and debugger internals.

* Prediction (written before the first run)

The hypothesis is the suggested one; the prediction below is what I
expect to measure, and it already disagrees with the first clause.

1. *Load: refuted.*  inspect.fs uses about two dozen 0.7.3 internals
   with no =[defined]= guard (=>head-noprim=, =threaded>name=, =look=,
   =interpret1=, =handler-intro,=, =.debugline-stderr=, =loadfilename#>str=,
   =compile-sourcepos=, and debug.fs's =DebugLoop=, =dbg-ip=, =c-pass=,
   =DebugMode=, =NestXT=, =nestXT-checkSpecial=, =(_debug)=, =Leave-D=,
   =set-bp=, =restore-bp=, =d.s=).  At least one of them is gone or renamed
   in 1.0, so the load stops with "Undefined word" at the first one, and
   every public word defined after that line is missing.  I expect the
   first stop inside =colon-xt?= (line 39, =>head-noprim=), which would
   leave only =inspect-version= defined.  Redefinition warnings are
   likely too, since 1.0 has many more words in its image.
2. *Words:* whatever is defined before the stopping line works;
   everything after it is "Undefined word".  If the load gets further
   than predicted, =.stacks= prints data and float stacks correctly but
   names no return addresses, and =dbg-fix= crashes or patches the wrong
   cells.
3. *Goldens:* every one of the 36 tests fails in every 1.0 engine, at
   least on the load error in stderr; none passes by accident.
4. *Property tests:* =pbt/gforth_run.py= runs whatever =gforth= is first
   on =PATH=, so it can be pointed at 1.0 without editing it.  The smoke
   step has no hello record, so =gmake -C pbt check= fails.
5. *Log:* if =log-on= is never defined there is no log to validate.  If it
   is, every line validates and starts with ={"v":1,=, and =hello.gforth=
   is ="1.0.0"= / ="1.0.1"=: the JSON writer uses only standard words
   (=emit=, =type=, =.r=, =fs.=, =pick=, =fpick=).
6. *Engines:* 1.0 builds =gforth=, =gforth-fast= and =gforth-itc= (and
   =gforth-ditc=); the load result is the same in each.

* Gate

1. *Provenance.*  For each tarball: its SHA-256, and what it was checked
   against (a published checksum, a signature, or none found: recorded
   either way).  The build route (macOS from source, or the
   =forthy42/gforth= image) and each binary's =version-string=.  The
   inspector is =v0.1.1:env/inspect.fs=, blob =82860519a7d3=.
2. *Isolation (E-10).*  Every gforth run gets its own temp dir as cwd,
   =HOME= and =XDG_STATE_HOME=, with =GFORTH_INSPECT_LOG_DIR= inside it, and
   loads files by relative name.  After the runs the real
   =~/.local/state/gforth-inspect/stacks.jsonl= has the same size and
   mtime as before them (#46).
3. *Calibration.*  The probe harness runs first on stock gforth 0.7.3,
   where every public word must come out "works" in all three engines;
   a harness that cannot say "works" there cannot say "fails" on 1.0.
4. *Measurements*, for 1.0.0 and 1.0.1 and each engine the build
   provides:
   - load: =gforth inspect.fs -e bye=, its exit status, every warning,
     redefinition and error;
   - each public word (=.stacks .rs .input .cs ~~~ all-~~ dbg-fix dbg+
     log-on log-off log-where log-id fclearstack inspect-version rs-full
     contract-version=), each in its own process: works, errors, or wrong
     output (wrong = differs from 0.7.3's output of the same probe,
     after masking addresses and paths);
   - =test/run.sh= with the 1.0 binaries first on =PATH=: pass/fail per
     test and engine;
   - =gmake -C pbt check= with the root Makefile's =PBT_ENV=, the 1.0
     binaries first on =PATH=;
   - every =stacks.jsonl= written: =test/validate.py= against the schema,
     the I-1 prefix, and =hello.gforth=;
   - for each failure, the 0.7.3 internal behind it and a one-line
     reproducer that runs on plain gforth 1.0, without inspect.fs.
5. *Verdict.*  The hypothesis holds if the load is free of errors in
   every 1.0 engine, the log validates and keeps I-1, and =dbg-fix=,
   =dbg+= and =.rs= fail.  Otherwise it is refuted, and the Log says which
   clause failed.

* Log

** 2026-11-22 provenance: where 1.0.0 and 1.0.1 came from

The URLs in the brief, =forth/gforth/gforth-1.0.0.tar.xz= and
=gforth-1.0.1.tar.xz= at the top of the download directory, no longer
hold them: the top level now carries =gforth-1.0.2.tar.xz= (a later point
release, not tested here), =gforth-1.0.0.tar.xz= answers 404, and
=gforth-1.0.1.tar.xz= has moved to =old/=.  Both releases are under
=forth/gforth/Snapshots/1.0.0/= and =Snapshots/1.0.1/=, each with three
detached signatures: =.asc= (armoured OpenPGP), =.sig= (binary OpenPGP)
and =.s2o= (a net2o signature).  No checksum file is published, and the
announcement on the gforth list gives none.

Each tarball went into its own new empty directory.

| tarball             | SHA-256                                                          | bytes   |
|---------------------+------------------------------------------------------------------+---------|
| gforth-1.0.0.tar.xz | 79c880b68a4a9aa817b7067c21b79acd5b07149fad78f3f630320db410886fa6 | 4840516 |
| gforth-1.0.1.tar.xz | d7cb2a1d0d0d9e4d895bce0739179ba97037a9da790fea536afcdc91f6d93d00 | 4845192 |

Verification: =gpg --verify= of both =.asc= and both =.sig= says "Good
signature", EdDSA key =04880DE6ECB06FC8EE9C3AF43B64AEC1E0B7BDE0=, in a
throw-away =GNUPGHOME=.  The key was fetched by that fingerprint from
keyserver.ubuntu.com (keys.openpgp.org has no copy); its uid names a
gforth maintainer.  It is not in the GNU keyring (=gnu-keyring.gpg=), and
the fingerprint was not confirmed through a second channel, so this
proves the four files agree with one key, not that the key is the
project's.  All four signatures are dated 2026-11-02: 1.0.0 (released
2026-10-25) was signed a week after its release.  The =.s2o= files were
not checked (no net2o here).  The =old/= copy of 1.0.1 is byte-identical
to the =Snapshots/= one.

Build route: macOS (arm64, Darwin 24) from source, into a private prefix
in the session's scratch dir, =nice -n 19 gmake -j2=.  Two obstacles:
- =configure= refuses clang outright ("Clang has a long unfixed bug that
  makes it unsuitable to compile Gforth"), so Apple's =cc= is out;
- Homebrew's gcc 16.1.0 cannot compile =#include <stdio.h>= against the
  installed SDKs (15.2 and older): its fixincluded =_stdio.h= includes
  =_bounds.h=, which only newer SDKs have.  A one-file shim directory,
  passed as =CC="gcc-16 -idirafter <shim>"=, defines the nine
  bounds-safety macros =_stdio.h= uses as empty (they are no-ops without
  =-fbounds-safety=).  The shim touches only that system header; no
  gforth source is changed.

** 2026-11-22 calibration on 0.7.3 (gate 3)

=probe.sh= (one process per probe, E-10 isolation; inspector from
=ref:v0.1.1 blob:82860519a7d3=) on stock Homebrew 0.7.3, all three
engines: 16 of 16 probes exit 0 with the expected output, and the masked
outputs are byte-identical across =gforth=, =gforth-fast= and
=gforth-itc=.  Two probes were fixed before this run, both harness bugs:
=cs.fs= looped for ever on =0 UNTIL= (now =-1 UNTIL=), and =dbg-nest.fs=
pressed =n= on a literal (now Enter, then =n= on =sq=).

=internals.sh= lists 197 distinct system words that inspect.fs names
(comments, strings and its own definitions removed); all 197 are found
by =find-name= in all of 0.7.3's engines, so the tokenizer drops nothing
0.7.3 lacks.

The real =~/.local/state/gforth-inspect/stacks.jsonl= before any run:
2600 bytes, mtime 1795358250 (gate 2 baseline).

** 2026-11-22 builds, and a libcc wrapper that is not about the inspector

Both builds finished (=gmake -j2=, nice 19) and gave =gforth=,
=gforth-fast=, =gforth-itc= and =gforth-ditc=, each reporting
=version-string= =1.0.0= / =1.0.1=.  =gmake install= stops in
=install-libcc= on the two X11 wrappers (=libgfx=, =libgfxrandr=: no X11
headers), after the other libcc wrappers are installed; =gmake -k install=
completes everything else.

On this install every start of every engine prints two =dlopen(...)=
errors to stderr, for =libgflibc.so= and =libgfpthread.so=: the first
entry on 1.0's libcc search path is =$HOME/.cache/gforth/arm64/libcc-tmp/.libs/=,
which a fresh HOME does not have, and =engine/support.c= prints
=dlerror()= on each miss before the next entry (the installed
=libcc-named/=) succeeds.  That would fail every golden on stderr alone,
for a reason that has nothing to do with inspect.fs.  So every run below
goes through a four-line wrapper per engine that sets =libccnameddir= to a
directory whose =.libs= links to the installed =libcc-named/=; with it,
start-up is silent and creates nothing in HOME.  Whether a packaged 1.0
(Homebrew, Debian) shows the same noise was not checked.

** 2026-11-22 results: load, words, internals

Runs: =probe.sh= on 1.0.0 and 1.0.1, four engines each, inspector
=ref:v0.1.1 blob:82860519a7d3=; =internals.sh= per engine.  Summaries
are committed as =results/probes.tsv= (=summarize.sh=, verdict per run,
engine and probe against 0.7.3's output) and =results/internals.tsv=.

*Load: refuted, in all eight engine builds.*  =gforth inspect.fs -e bye=
exits 1:

#+begin_example
inspect.fs:40:5: warning: name>int is obsolete
inspect.fs:56:26: warning: .name is obsolete
inspect.fs:73:13: error: Undefined word
    dup ['] >>>interpret1<<< = over ['] interpret = or over ['] handler-intro, = or
#+end_example

gforth 1.0 also stops processing the command line at that error, so a
program named after inspect.fs never runs: all 16 public-word probes
(and json-parts) end with the same error and exit 1, no log is written,
and the probe's own output never appears.  Only =colon-xt?=, =enclosing=,
=.where=, =stack-region?= and =inspect-version= get defined, and
=inspect-version= is never reachable from the command line.  The
prediction named the wrong first stop (line 39, =>head-noprim=):
=>head-noprim= still exists in 1.0, it just means something else (below).

*Internals.*  Of the 197 system words inspect.fs names, 181 are found in
1.0.x's image and 16 are not (identical in 1.0.0 and 1.0.1, and in every
engine).  13 of the 16 are debug.fs internals that 1.0 keeps in the
=see-voc= wordlist (=also see-voc= finds them); three are gone:
=interpret1=, =handler-intro,= and =.debugline-stderr=.

*Diagnostic second layer.*  To see what fails after the load error,
=shim-1.0.fs= is loaded first: =also see-voc=, and the three missing
names defined as empty words that never appear on a return stack.  It
is not a port and makes nothing correct; it only lets names resolve.
Shimmed, the load completes with warnings (=name>int= and =.name=
obsolete, five times; ="0." is a double-cell integer= twice;
=redefined .stacks=, since 1.0's =status-line.fs= has its own).  Then,
the same in 1.0.0 and 1.0.1 and in all four engines unless noted:
- works: =inspect-version=, =contract-version=, =.input=, =fclearstack=
  (1.0 has its own, so the =[undefined]= guard keeps it), =log-off=,
  =log-where=, =log-id=, =log-on= and its hello record;
- errors, "Invalid memory address", then exit 139 (SIGSEGV): every word
  that walks the return stack, which is =.stacks=, =.rs=, =rs-full=, =~~~=,
  =all-~~= =~~= and every snapshot record.  The crash is in =colon-xt?=:
  1.0's =>head-noprim= returns its argument (an nt is the xt now), so on
  an arbitrary cell it hands =name>int= a non-header and dies;
- errors, "Cannot allocate memory" in =patch-colon=: =dbg-fix=, =dbg+=, in
  =gforth=, =gforth-fast= and =gforth-ditc=.  Rolling =dp= back into an
  existing body and =compile,=-ing there trips 1.0's peephole bitmap;
- wrong: =dbg-fix= / =dbg+= in =gforth-itc= patch without error, but =dbg t=
  prints "(not a colon definition: stepped over)" and just runs =t=: no
  step is shown, because =colon-xt?= tests =xt @ docol: == and in 1.0 a
  colon word's code field cell is not =docol:= (=>code-address= is);
- wrong: =.cs= prints its header and no items: 1.0's control-flow stack
  items are tagged with addresses, not 0.7.3's small integers 0 to 5.

The JSON writer itself is unchanged: =json-data=, =json-float= and
=json-input= on 1.0.x print byte-for-byte what they print on 0.7.3
(=json-parts=), including =-0.0=, =1e300= and 17-digit floats.

** 2026-11-22 the log, and the goldens

Correction to the entry above: its "works" list named =log-off=,
=log-where= and =log-id= before any probe had used them without a
snapshot (the =log= probe dies at its first =.stacks=).  The new
=log-plain= probe (=log-on=, =log-id=, =log-where=, =log-off=, =log-on=
=log-off=, no snapshot) now does: unshimmed it fails like every probe
(exit 1, the load error); shimmed it works in all eight engine builds, and
writes two hello records.

*Log (gate 4, I-1).*  Unshimmed, 1.0.x writes no log at all: =log-on= is
never defined.  Shimmed, 24 =stacks.jsonl= files were written (=log=,
=log-tilde=, =log-plain= × 4 engines × 2 versions), 32 lines, every one a
hello record and every one the same apart from =t=:
={"v":1,"event":"hello","t":T,"gforth":"1.0.0","inspect":"0.1.1","contract":"1.1"}=
(="1.0.1"= for 1.0.1).  All 32 validate against
=contract/stacks-log.schema.json= (=test/validate.py=, jsonschema and the
built-in validator), all begin with ={"v":1,= (I-1, D-38), and
=test/consumer.py 1.1= accepts every file.  =hello.gforth= is gforth's own
=version-string=, so a consumer can see a 1.0 producer for what it is.
No snapshot record was ever written on 1.0: every path to one walks the
return stack and crashes first, so whether a 1.0 snapshot would validate
is not measured.  The parts that do not walk the return stack print
exactly what 0.7.3 prints (=json-parts=).

*Goldens.*  =test/run.sh -e "gforth gforth-fast gforth-itc gforth-ditc"=
with the wrapped 1.0 engines first on =PATH= (it runs =env/inspect.fs=,
the same blob =82860519a7d3=): 0 of 148 cases pass on 1.0.0, 0 of 148 on
1.0.1 (37 tests × 4 engines; =idle= skipped).  144 fail with "exit status
1, want 0" and a diff that starts at the load error; the other 4 are
=demo= (=noinspect=, it loads =env/brk.fs=), which dies with "Invalid
memory address" and exit 139 at its first =brk=: =call-c= on a raw
=lib-sym= address no longer works.  Control, same tree, stock 0.7.3: 111
of 111 pass.  Per case: =results/goldens.tsv=.

The runner would not have caught 1.0's redefinitions: it looks for
=^redefined =, 0.7.3's format, and 1.0 writes =file:line:col: warning:
redefined .stacks=.  That only matters once the load gets past line 73.

*Isolation.*  Probes, goldens and reproducers all ran with their own
temp dir as cwd, =HOME= and =XDG_STATE_HOME=; =probe.sh= found no stray
=stacks.jsonl= outside the run's own =GFORTH_INSPECT_LOG_DIR=.
