* Hypothesis

H1. For every producer transition A → B on the version ledger below,
[[file:../../docs/RELEASING.org::*Rulings][RELEASING.org::*Rulings]] predict each consumer's behaviour (follow; same output;
stop with a message), and the consumers do exactly that, with 0 to 5 live
producer sessions.

H2. [[file:../../contract/CONSUMER-AGENTS.md][CONSUMER-AGENTS.md]] "A new version", steps 1–5, can be executed as
written for every transition, by a scripted consumer.

H3. The envelope (=v=, =event=, =t=, and =hello.contract=) is separable from
the payload: every record from every ledger version and every fixture,
including contract 10.0, validates against one envelope schema, and every
consumer handles a record it cannot use by stopping with a message, never by
crashing or emitting wrong data. (D-36: the envelope is frozen and versioned
by 1.0.0.)

H4. The corpus is complete: every schema path, value class and event is
exercised under every version that supports it.

H5. Compound version check. The version is a tuple, checked together: record
=v=, =hello.contract=, =hello.inspect=, the schema's =$schema= dialect
(=https://json-schema.org/draft/2020-12/schema=), =x-version= (1) and
=x-contract= (1.1), and the API spec of =GET /stacks=. A consumer that checks
one field accepts a stream another field says it cannot read.

* Gate

1. Calibrate first: each consumer-behaviour check red on a planted fault
   (a checker with its version stop disabled; a fixture labelled PATCH that
   changes jq output; a consumer that crashes on X5 reported as "stopped").
2. Matrix: every ledger transition in sequence (V0 → … → V5 → F1 → … → F5),
   plus skips V2 → V5, Vc → V5, V5 → F4, V5 → F5; × N ∈ {0..5} × 4 orders;
   every X-stream × every consumer. All 3 engines across N ≥ 1.
3. Every cell: observed vs the ruling's prediction, with xrid. A mismatch is
   a finding, never a re-labelled ruling.
4. H2: each of the five steps logged per transition: ran / failed as
   written / not applicable. A step that fails as written is a finding →
   a CONSUMER-AGENTS.md change by PR, in D-9 order.
5. H3: an envelope schema candidate (=contract/= change proposal only, in the
   PR body; E-6) that every ledger, fixture and X-stream record validates
   against or is rejected by with a named reason.
6. H5: a compound check (all tuple fields agree, or stop naming the field)
   as a proposal in the PR body, run over every X9 cell; plus an OpenAPI
   3.1 draft for =GET /stacks= whose =info.version= is in the tuple.
7. H4: coverage table (schema path × value class × version); every gap
   closed by a corpus scenario before the gate passes.
8. Outputs: =versions.org= (the ledger with rulings), =matrix.tsv=, the
   coverage table, findings as issues. Counts and hashes only for Vc.
