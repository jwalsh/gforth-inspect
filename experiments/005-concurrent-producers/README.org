#+TITLE: 005 concurrent-producers: two gforths, one log (issue #17)
#+DATE: 2026-11-21
#+STARTUP: showall

* Hypothesis

When N gforth processes (N from 2 to 4), each with =log-on=, write
snapshots to one =stacks.jsonl= in any interleaving, every line of the file
parses as JSON, validates against the schema, and every record each
producer wrote is present exactly once. Each producer tags its snapshots
with =log-id=, so a record can be traced to its writer. This is producer
obligation 1 in CONSUMERS.org: append-only, one complete object per line.

* Prediction (written before the first run)

Refuted on b1c162e and on harden's head. =log-on= seeks to the end once,
and every later write goes to that file descriptor's stale offset, so a
second producer's records are overwritten and a fragment is left behind
(#17). It holds on any inspect.fs that seeks to the end before each record
(=file-size= + =reposition-file= in =log-write=, the downstream deviation).
Writes of under one page are not split by the OS, so seek-then-write races
only within a window narrower than one record. The property should hold
in practice for N up to 4 at the interleavings generated here, and the run
reports how often a race was even possible.

* Gate

1. *Interleavings.* Hypothesis generates the schedule: which producer
   writes next and how many snapshots it writes, from 2 to 4 producers.
   The schedule is driven deterministically, by feeding each gforth its
   stdin one line at a time and waiting for that record to land, not by
   sleeping. Run at least 200 schedules on =gforth=, and 50 each on
   =gforth-fast= and =gforth-itc=.
2. *Result.* Report per ref: lines that fail to parse, records lost,
   records duplicated. Refs: =b1c162e=, harden's head (pinned by hash), and
   a patched copy of harden with the seek-before-write fix. That copy is a
   test fixture made by sed in a temp dir, not a change to =env/=.
3. *Also uncoordinated.* Run 50 schedules where the producers really do
   run concurrently, with no stdin pacing, and report the result as its
   own line. It is evidence about the race window, not part of the pass
   or fail.
4. *Calibration.* =pbt/calibrate/005-*.sh= runs the test against harden's
   head, unpatched. It must go red with a parse failure or a lost record,
   and green on the patched copy.
5. Until the producer fix lands, the property test is a strict xfail that
   cites #17. It turns red (XPASS) the moment harden is fixed, and that is
   the signal to remove the xfail.

* Log

** 2026-11-21 setup: refs, pacing, decision on the xfail

Provenance, pinned at the start:
- =ref:b1c162e@b1c162e blob:76d34db7cd61=
- =ref:8deb780@8deb780 blob:a7e5c141af51= (harden's head, local).  During
  the run the =harden= name moved to =10a0da4=, a release-check change; the
  inspect.fs blob is the same, =a7e5c141af51=.
- patched: =8deb780 blob:a7e5c141af51 +seek-per-write=, made in a temp dir
  by the sed in =pbt/_005_helpers.py= (=FIX_SED=).  It changes one line of
  =log-write=, before =base @ >r decimal=:
  =log-fid @ file-size throw log-fid @ reposition-file throw=.

Pacing, checked by hand: gforth 0.7.3 on a pipe (no TTY) reads stdin a
line at a time and runs each line as it arrives.  It echoes the line and
flushes stdout before it reads the next, so =cr ." #ACK n" cr= at the end of
each line is a reliable completion signal.  The marker has to start its own
stdout line: the echo of the input holds the same characters.  Without a
TTY no history prompt is involved, but gforth still writes
=.gforth-history= to =$HOME=, so each producer gets its own temp =HOME=.
No FIFO or =key= tricks were needed.  After the ACK the launcher polls the
log for the record's marker (data stack =[5005, producer, seq]=, since
b1c162e has no =log-id=; on harden the =id= tag =p<producer>= is also
checked).  A hello is awaited as the last line of the file: counting hellos
does not work on an unfixed ref, where an earlier hello may be overwritten.

Decision (coordinator, 2026-11-21): the default-ref test is ref-aware, not
a blanket strict xfail.  It is xfail(strict) citing #17 only when the
inspect.fs under test has no =reposition-file= inside =log-write=, and a
plain test otherwise.  Reason: the #17 fix is about to land on =harden=
through its own PR.  A blanket strict xfail would turn the suite red (XPASS)
on main the moment it lands, for a change that is correct; the ref-aware
form stays green on either side of the fix, and still goes red if a fixed
producer regresses, because a fixed source runs as a plain test.  Gate item
5 asked for the XPASS signal; this replaces it with "the xfail lifts itself,
and the test then has to pass".

Calibration runs with =--runxfail= so the red on unpatched harden is
visible; the patched copy must be detected as fixed and pass.

** 2026-11-21 review fixes

=/code-review high= on #18 found ten issues.  Two change what the setup
entry says:
- The xfail is no longer decided by grepping for =reposition-file= in
  =log-write=: a fix in another shape (a helper word, an append-mode open in
  =log-on=) would have stayed xfail and gone XPASS.  It is now xfail(strict)
  only while =log-on= and =log-write= are word for word those of a pinned
  unfixed ref (b1c162e or 8deb780).  Any change to either word makes the
  test plain, which then has to pass; edits elsewhere in inspect.fs keep
  the xfail.  Same intent as the coordinator's decision, a sturdier test.
- The fix has one definition, =patched()= in =pbt/_005_helpers.py=; the

  sed form, for the harden PR, is in the PR body.

| ref     | lines | parse | lost  | hellos |
|---------+-------+-------+-------+--------|
| b1c162e |  7466 |   173 |  9348 | 70/159 |
| 8deb780 |  6652 |   203 | 10184 | 62/159 |
| patched | 11884 |   622 |  5423 | 114/159 |

The fix roughly halves the loss but does not stop it.  Reading log-write,
the seek happens before the record is formatted, and the record reaches
the kernel only at =flush-file=, so the race window covers the formatting,
not one write call.  That is an inference from the code; it was not
measured.  Only an =O_APPEND= open removes the window, and gforth 0.7.3
has no append fam.  Formatting into a buffer and then seeking and writing
it in one =write-file= would narrow the window to two system calls.

Verdict per gate item:
1. Interleavings: met.  Hypothesis-generated schedules of 2 to 4
   producers, driven line by line with an ACK and a poll of the log, no
   sleeps; 200 / 50 / 50 per engine on every ref.
2. Result: hypothesis refuted on b1c162e and on 8deb780, as predicted (the
   counts are above); it holds on the patched copy under pacing.
3. Uncoordinated: reported above.  This part of the prediction is
   refuted: it said the fixed producer would hold "in practice" with N up
   to 4, and it loses records under real concurrency.  The seek-per-write
   fix closes #17 as a sequential bug, not as a concurrent one.
4. Calibration: met.  =pbt/calibrate/005-seek-per-write.sh= is red on
   unpatched harden on all three engines with "parse failures 1 ... lost
   1", and green on the patched copy.
5. Xfail: met in its changed form (decision above).  Strict xfail citing
   #17 while the write path is that of a pinned unfixed ref; when the fix
   lands on harden the test becomes a plain one and has to pass.

** 2026-11-21 harden moved to c1a6a3a: pins, and the reworked fix

The =harden= name now points at =c1a6a3a= (blob =af95cdf354af=), which
carries the #17 rework: the whole record is built in a buffer, then one
seek and one =write-file= of the whole line.  "harden's head, unpatched"
in the gate now means the pinned =10a0da4= (blob =a7e5c141af51=, the same
inspect.fs as =8deb780= where 005 started).  It is pinned in code as
=HARDEN_REF= in =pbt/_005_helpers.py=, and the calibration defaults to it.
The moving =harden= name no longer stands for "unfixed".  =c1a6a3a= is
pinned as =FIXED_REF= and is a fourth side in the reports.

The ref-aware xfail treats =c1a6a3a= as fixed: its =log-write= differs
from both pinned unfixed refs, so =test_concurrent_producers= runs as a
plain test, and it passes on 201 / 51 / 51 schedules with every count at
0.  =test_patched_copy= skips, because the write path changed.

Run: =gmake -C pbt check SEED=5005= gave 98 passed, 3 skipped and 1
xfailed (the xfail is not one of 005's); =gmake -C pbt calibrate= was red
as expected on all 14 scripts.  Paced, =c1a6a3a= matches the seek-only
patch: 0 parse failures, 0 lost and 0 duplicated on every engine.

Uncoordinated, 50 runs, seed 5005.  The schedules are the same for every
side, so every side was asked for 16571 snapshots and 159 hellos.  The

=O_APPEND= would close the window, and gforth 0.7.3 has no append fam.
This stays report-only (gate item 3).
