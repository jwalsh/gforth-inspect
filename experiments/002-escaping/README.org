#+TITLE: 002 escaping: input.text survives JSON
#+DATE: 2026-11-21
#+STARTUP: showall

* Hypothesis

For any input line taken by =.stacks= under =log-on=, the snapshot line in
=stacks.jsonl= decodes as strict UTF-8 and parses as strict JSON (Python
=json.loads=, with no =strict=False=). Its =input.text= equals the source
line with every byte below 0x20 mapped to a space, and =input.in= is the
=>IN= at the snapshot.

The generated lines can contain =\"=, =\\=, every control byte, DEL,
multi-byte UTF-8, astral-plane characters and lone bytes of 0x80 and above,
and can run from 0 bytes up to the longest line gforth's input buffer
accepts. One way to build a case: =.stacks \ <generated>=, which puts the
generated text in a comment, so the line stays valid Forth while =source=
returns all of it. Also try a generated line that sits before the
=.stacks=, inside =s" ..."= or =( ... )=, where it is still legal Forth.

* Prediction (written before the first run)

Valid UTF-8 round-trips, and so do quotes and backslashes. DEL passes
through raw, which JSON allows. Lone high bytes come through raw and make
the line invalid UTF-8, so the property is refuted for non-UTF-8 input.
That would be a finding about the contract: the schema says =string= and
does not say what happens to non-UTF-8 source.

* Gate

1. *Volume.* At least 1000 examples on =gforth=, and 200 each on
   =gforth-fast= and =gforth-itc=. Escaping should not depend on the
   engine, and the smaller runs check that it does not.
2. *Result.* The pass rate is reported per input class (ASCII, controls,
   valid UTF-8, invalid bytes, long lines). Each failing class gets one
   shrunk reproducer.
3. *Calibration.* =pbt/calibrate/002-*.sh= runs the tests against planted
   faults and must go red on each: (a) =json-str= does not escape =\=; (b)
   =json-str= leaves control bytes raw.

Out of scope: the stack fields (001).

* Log

** 2026-11-21 probes (by hand, before the property runs)

gforth 0.7.3, included file, all three engines.

- Line ends: LF, CR and CRLF each end a line; CRLF counts once, LF CR
  twice (=sourceline#= skips one).  No other byte does: 0x00-0x1f minus
  LF/CR, DEL and 0x80-0xff all stay in =source=.  Generated text therefore
  never holds LF or CR; =test_cr_lf_crlf_each_end_a_line= pins the model.
- Line length: no limit found.  A comment line of 1 MiB round-trips in
  every engine; 8, 32 and 128 MiB lines do in =gforth= (0.5 s, 2 s, 9 s).
  The =long= class draws 4-64 KiB (a drawn chunk repeated, because
  Hypothesis cannot draw 64 KiB of entropy per line), and
  =test_one_mebibyte_line= runs a fixed 1 MiB line per engine.
- =>IN= at =.stacks= is just past the word plus its one delimiter, if any:
  7 for a bare =.stacks=, 8 for =.stacks \ ...=.  Tab is a delimiter for
  the outer interpreter, 0x01 and DEL are not.
- Start-up is about 6 ms a process, so one gforth run per Hypothesis
  example (a batch of 1-20 lines, 1-4 for =long=) is cheap.

** 2026-11-21 verdict

1. *Volume*: met.  1000 examples per class on =gforth=, 200 per class on
   =gforth-fast= and =gforth-itc=, in both runs.  No engine differed.
2. *Result*: per class above.  At b1c162e the hypothesis holds for ASCII,
   controls, valid UTF-8 and long lines and is refuted for invalid bytes,
   as predicted; reproducer above.  At the head of =harden= (0.1.0) every
   class passes against the contract's oracle.
3. *Calibration*: met.  (a) and (b) go red on every engine, for the
   expected reason, against both inspector versions.

Contract findings.  b1c162e broke the "UTF-8" line of the contract for
non-UTF-8 source; 0.1.0 fixes that by replacing each invalid byte with one
U+FFFD (per byte, not Unicode's maximal-subpart rule, so =E2 82= gives two;
the contract could say "each byte").  Two gaps remain.  The replacement is
lossy, so =text= no longer equals the source for such lines and nothing in
the record says so; a flag or a byte-exact companion field would.  And
=input.in= counts bytes of the raw line while =text= is a JSON string of
characters, so a consumer that places a caret at =text[in]= is off by one
per extra byte of every multi-byte character before it; the contract
should say that =in= is a byte offset into the UTF-8 (raw) source line.
