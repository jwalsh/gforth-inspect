#+TITLE: Findings 2026-11-21: gforth 0.7.3 by hand, before the tests
#+STARTUP: showall

* lldb: exact only at a Forth-side breakpoint

=brk= enters C via =call-c=, which flushes the VM registers to
=gforth_SP= / =FP= / =RP= / =LP=. Elsewhere lldb guesses: no arm64 port in
0.7.3, registers move at =-O2=, gforth-fast keeps TOS in a register. A
=-g -O0= build is exact. lldb can't attach from a sandboxed agent session.
*Rule: no lldb in any live pipeline.*

* Threaded code differs from what the stock tools assume

- xt = code-field address. =dodoes:= pushes =>body=. A =does>= word is
  =[dodoes:][does-code][body]=.
- Direct-threaded engines: a colon call is two cells, =call <body>=. Stock
  =dbg= is ITC-only (=debug.fs=: "!!! dependency: ITC") and crashes on the
  first step in gforth and gforth-fast. =dbg-fix= and =nestXT+= insert the
  two-cell breakpoint.
- A control-flow stack item is three cells (orig / dest / do-dest).
- =pause= saves sp/fp/rp/lp in the task area; a server task can read the
  REPL task's stacks from there.

* An inspector that reads the return stack moves it

=.stacks= once printed its own frame's return stack, not its caller's:
plausible and wrong. Hence non-interference and faithfulness are separate
properties (001), and =.stacks=, =~~~=, =all-~~= =~~= are tested as three
paths: each stores =snap-rp= differently.

* Sockets

- =unix/socket.fs= needs =C_INCLUDE_PATH= set to the gforth bottle's
  =include/= (Homebrew's libcc header path is wrong).
- =create-server= binds 0.0.0.0: bind 127.0.0.1 yourself.
- =tasker.fs= sets =key= to =task-key=: the REPL pauses while idle.
- A 30-line server-task prototype found its socket fd on the REPL's data
  stack: the two tasks shared one stack.

* Floats (confirmed by 001, fixed in #1)

=-0e= logged as =0.00000000000000E0=, sign lost; =json-f= printed through
=fs.= with 15 significant digits. Records did not round-trip.
