#+TITLE: Releasing
#+STARTUP: showall

Downstream projects use only tagged releases, never branches. That makes a
release a promise, and this file says what it promises. Who produces the
stream, who consumes it, and what each owes the other is set out in
[[file:../contract/CONSUMERS.org][contract/CONSUMERS.org]]; what a consuming agent reads is
[[file:../contract/CONSUMER-AGENTS.md][contract/CONSUMER-AGENTS.md]], and the skill an agent installs is
[[file:../contract/skill/SKILL.md][contract/skill/SKILL.md]]. All three ship with every release: a consumer
gets the inspector, the guidelines and the skill, never this repository's
execution (tests, scripts, CI, experiments).

* What a release is

- A tag =vMAJOR.MINOR.PATCH= on =main=, published as a GitHub Release.
- *Every release is a full release, marked Latest.* From v0.3.1 on, each
  tag is published as a GitHub release, not a prerelease, and marked Latest
  (decision D-47, 2026-11-25). v0.1.0 to v0.3.0 were published as
  prereleases, to rehearse this process (D-41). The label is all that
  changed: the first stable tag is still v0.5.0 or v1.0.0 (D-32), and a
  release before it promises nothing stable (Rulings). Until then the
  coordinators commit directly to =main= while the repository is under
  review, and downstream projects may keep their own local copies.
- Each release carries its own spec and contract. The assets are
  self-contained and flat (no directories):

  | asset                    | from                              |
  |--------------------------+-----------------------------------|
  | =inspect.fs=             | =env/inspect.fs=                  |
  | =stacks-log.schema.json= | =contract/stacks-log.schema.json= |
  | =stacks-log.org=         | =contract/stacks-log.org=         |
  | =CONSUMERS.org=          | =contract/CONSUMERS.org=          |
  | =CONSUMER-AGENTS.md=     | =contract/CONSUMER-AGENTS.md=     |
  | =SKILL.md=               | =contract/skill/SKILL.md=         |
  | =WORDS.org=              | =contract/WORDS.org= (since 0.2.0) |
  | =SHA256SUMS=             | covering the seven above          |

  Downstream projects depend on these file names, so renaming, removing or
  moving an asset is a MAJOR change. The prose files have to render on
  their own: in the =dist/= copies, every link between them names its
  sibling in the same directory (=CONSUMERS.org=, not =../CONSUMERS.org=),
  and a link to anything else is an absolute URL pinned to the tag. A
  consumer reads the schema from its downloaded copy, never from a branch.
  =canvas.fs= is not part of this project and never ships. It was a test
  bed on =harden= and was removed before the first tag (decision 27).
- =inspect.fs= begins with these two lines:
  #+begin_example
  \ gforth-inspect vX.Y.Z
  \ stacks-log schema v1
  #+end_example
- =inspect-version ( -- c-addr u )= returns ="X.Y.Z"=, and the =hello= record
  carries ="inspect":"X.Y.Z"= and ="contract":"MAJOR.MINOR"=, the latter equal
  to the schema's =x-contract=. inspect 0.4.0 (this release) announces
  contract 1.2. A consumer that follows CONSUMERS.org refuses a stream that
  has no =contract=.

* Stable API, and what bumps what

*The rule: anything that would break one of the three reference consumers
below, as they are today, is a new record =v= and a MAJOR release. That
holds even where the schema would technically allow the change.*

| change                                                                                                                                                                                    | bump                                      |
|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+-------------------------------------------|
| remove or rename a key or an event; change a type; change what =null= means; split a record across lines; change the default file location; print numbers that decode to different values | MAJOR, plus new record =v= and =x-version= |
| remove a word, or change a stack effect                                                                                                                                                   | MAJOR                                     |
| a new optional key; a new event type the consumers can ignore; a new word                                                                                                                 | MINOR                                     |
| a fix that keeps every word's stack effect, and every record as the consumers read it                                                                                                     | PATCH                                     |

** The reference consumers

Each is a release-gate test (=pbt/consumers/=) and is frozen as written.
Changing a frozen consumer to make it pass is itself a breaking change.

1. *Simple CLI tooling.*
   =tail -f stacks.jsonl | jq -c '{e:.event,w:.where,d:.data,f:.float}'=.
   It relies on one complete object per line, append-only writes, stable
   key names, and numbers that decode to the same values.
2. *An editor dashboard and checker.* It reads the last line, validates
   it against the schema with a subset validator, and renders
   =data= / =float= / =rs= / =input=. The course's =course-forth-dashboard=
   and =course-forth-check= are the instances. Their wording is in the
   course's =stacks-log.org= under "Compatibility".
3. *A mock API server.* =GET /stacks= serves the last record as-is.

A consumer must ignore keys it does not know, and the gate checks that
too: every produced record has an unknown key injected, and all three
consumers still give the same output.

** Rulings

Two cases that the table alone did not settle. Both were found by
experiment 004:

- *A fix toward the truth is not a break.* Suppose a number or a string
  decodes differently, and the new value matches the true state more
  closely than the old one: =fp@= bits for a float, the source bytes for
  =input.text=. That is a PATCH. Examples are #1 (17 digits, =-0.0=) and the
  0.1.0 escaping. A consumer that relied on the wrong value was relying on
  a bug. The change log still records the fix.
- *The first stable tag binds.* b1c162e was an import, and v0.1.0 and
  the releases after it, up to the first stable tag, promise nothing
  stable. So moving the default log directory to =.../gforth-inspect/=
  breaks no released promise. Until the
  first stable tag the table is applied as a discipline, recorded in the
  change log, but a break costs a note, not a MAJOR. From that tag on it
  binds, and the default location falls under the MAJOR row.

The stable words: =.stacks .rs .input ~~~ .cs all-~~ dbg-fix dbg+ rs-full
fclearstack log-on log-off log-where log-id inspect-version
contract-version=. =contract-version ( -- c-addr u )= returns the announced
contract, the string in the hello record's ="contract":"1.2"=.

=log-id ( c-addr u -- )= (issue #3) copies up to 63 characters. Each later
snapshot carries ="id":"<tag>"=, and =s" " log-id= clears it, after which
the key is omitted. In the schema, =id= is an optional snapshot property
of type string, and =x-version= stays 1.

Log location: =$GFORTH_INSPECT_LOG_DIR=, then the project's =.env=, then
=${XDG_STATE_HOME:-~/.local/state}/gforth-inspect/<owner>/<repo>/<worktree>/=
(since 0.3.0; the exact rule and its reference implementation are in
=contract/stacks-log.org=, "Files"). A released file never
names a particular downstream project.

* Gate: a release comes only from green

1. =gmake test= passes: the golden files in all three engines, and every
   record validated against the schema.
2. =gmake -C pbt check PROFILE=ci= passes, and =gmake -C pbt calibrate=
   reports red on every planted fault. Both run with the release under test
   named as verify names it (=INSPECT_FS=, =SCHEMA_JSON=, =INSPECT_REF=HEAD=;
   see "Cutting one"), or 004 checks the pinned c0cab02 instead.
3. =scripts/privacy-scan.sh= is clean, over the tree and over the release
   assets themselves.
4. =grep -c course-repo= on the assets prints 0.
5. The release notes include the test summary (engines, case counts, and
   the Hypothesis seed) and a =Fixed:= line naming every issue the release
   fixes, for example =Fixed: #1, #4= (each fixing PR says =Closes #N=, which
   is what closes it on GitHub). Downstream projects use those
   numbers to retire their local patches (see below).

CI (=.github/workflows/verify.yml=, an Ubuntu runner with gforth 0.7.3 from
apt) runs on every pull request and every push to =main=. It runs
=gmake verify= against the tree's own =env/inspect.fs= and schema, which is
also what =pbt/= and =corpus/= read when nothing else is named. CI does not yet run the =PROFILE=ci= long run, scan the
release assets or grep them (2, 3 over =dist/=, and 4). Until it does,
whoever cuts the release runs those by hand and pastes the output into the
notes.

* Mainline protection

=main= is protected, so that what CI checks is what lands. The rule set is
[[file:../.github/branch-protection.json][.github/branch-protection.json]], in the shape the PUT endpoint takes:

| rule                                       | why                                                                       |
|--------------------------------------------+---------------------------------------------------------------------------|
| a pull request before merging, 0 approvals | one owner and several agents: the PR is the record, not a sign-off         |
| status check =verify=, strict from the first stable tag | a PR merges only when CI is green; from the first stable tag also on a head up to date with =main=. *Removed 2026-11-22* (D-40): GitHub Actions billing stopped every job, so the workflow was disabled and a local =gmake verify= on the PR's head, pasted into the PR body (REVIEW.md), became the gate. *2026-11-25* (D-48): the workflow runs again, on =ubuntu-latest= (#61), but the check stays off until CI is green on =main= (red from #62 and #60); until then the pasted local line is still the gate. Restoring it is part of 0.4.1: put ="required_status_checks": {"strict": false, "contexts": ["verify"]}= back in the JSON, PUT it |
| linear history                             | the repository squash-merges; =main= stays one commit per change          |
| no force pushes, no deletion               | tags and downstream =DEVIATIONS.org= rows point at =main='s commits       |
| conversation resolution                    | a review thread on the PR is resolved before merge, not left hanging      |
| =enforce_admins= false                     | admins can bypass, see the phases below                                   |

Merges are squash only, and head branches are not deleted on merge:
experiment branches are kept as records.

The check =verify= is the id of the job in =verify.yml=. The workflow's
name does not matter to the rule, but renaming the job, or giving it a
=name:=, does: every PR would then wait on a check that never reports.
Change the job and this rule set together.

** Phases

1. *Until the first stable tag.* The repository is under active review, and coordinators
   commit to =main= directly (coordination documents, as AGENTS.md says).
   =enforce_admins= is false, so admins bypass the PR and the check. For
   them the protection only stops force pushes and deletion. Anyone
   without admin rights merges only through a PR with =verify= green (while
   the check is off, D-48, with a green local =gmake verify= in its body). An
   agent that pushes with the owner's credentials is an admin to GitHub:
   for it, as for the owner, the PR and the green check are rules of
   AGENTS.md, not of the protection. The =verify= check is *not strict* in this
   phase: a PR needs a green run on its own head, not on the latest
   =main=. With strict on, every direct push to =main= restarted the
   23-minute CI of every queued PR (issue #26); =main='s own CI run after
   each merge catches the rare semantic clash instead.
2. *From the first stable tag.* =enforce_admins= goes to true, and every change, the
   owner's and the agents' included, goes through a PR. The PATCH below
   edits an existing =required_status_checks=, so the 0.4.1 restore (the
   PUT under "Changing the rules", D-48) has to land first; on a =null=
   block it fails and leaves only =enforce_admins= flipped:

   #+begin_src sh
   gh api -X POST repos/{owner}/{repo}/branches/main/protection/enforce_admins
   gh api -X PATCH repos/{owner}/{repo}/branches/main/protection/required_status_checks \
     -F strict=true -f 'contexts[]=verify'
   #+end_src

   Set ="enforce_admins": true= and ="strict": true= in
   =branch-protection.json= in the same change, so the file and the live
   rules agree. =-X DELETE= on the same
   path turns it back off, for an emergency.

** Changing the rules

Edit =.github/branch-protection.json= and this section in a PR. Once it
merges, apply the file and read the result back:

#+begin_src sh
gh api -X PUT repos/{owner}/{repo}/branches/main/protection --input .github/branch-protection.json
gh api repos/{owner}/{repo}/branches/main/protection
#+end_src

Run these from a checkout: =gh= fills in ={owner}/{repo}= from its remote.
A PUT replaces every rule, so always send the whole file. The read-back is
not a valid PUT body (it has =url= keys, and =enforce_admins= and
=required_linear_history= come back as ={"enabled": ...}= objects), so
compare it with the file, do not feed it back in.

* Cutting one

#+begin_src sh
git switch main && git pull --ff-only
# bump env/inspect.fs's header line, its inspect-version doc comment and the inspect-version word, and in
# the docs every "X.Y.Z (this release)" and "inspect":"X.Y.Z" example (scripts/check-current-version.sh,
# in verify, names each one; it also checks "announces contract" against the schema), then commit:
# chore(release): vX.Y.Z
# the demo (demo/tour.*) is re-recorded for a MAJOR or MINOR release only: a PATCH leaves its banner
# the PROFILE=ci run names the release under test, as verify's PBT_ENV does: bare, 004's new side is the pinned c0cab02 (#68)
gmake test && INSPECT_FS=$PWD/env/inspect.fs SCHEMA_JSON=$PWD/contract/stacks-log.schema.json INSPECT_REF=HEAD gmake -C pbt check PROFILE=ci && scripts/privacy-scan.sh
gmake release-check   # builds dist/ as below and checks it
# by hand, what release-check does:
mkdir -p dist && cp env/inspect.fs contract/stacks-log.schema.json contract/stacks-log.org contract/CONSUMERS.org contract/CONSUMER-AGENTS.md contract/skill/SKILL.md contract/WORDS.org dist/
scripts/dist-links.sh dist vX.Y.Z env/inspect.fs contract/stacks-log.schema.json contract/stacks-log.org contract/CONSUMERS.org contract/CONSUMER-AGENTS.md contract/skill/SKILL.md contract/WORDS.org   # flatten siblings, pin the rest to the tag
(cd dist && shasum -a 256 inspect.fs stacks-log.schema.json stacks-log.org CONSUMERS.org CONSUMER-AGENTS.md SKILL.md WORDS.org > SHA256SUMS)
scripts/privacy-scan.sh dist/*
git tag -a vX.Y.Z -m vX.Y.Z && git push origin vX.Y.Z
notes=$(mktemp)   # write the notes here: test summary and the Fixed: line (Gate, 5)
gh release create vX.Y.Z dist/* --latest --notes-file "$notes"   # a full release, marked Latest (D-47); notes live outside dist/, so dist/* is exactly the 8 assets
scripts/readme-release.sh vX.Y.Z    # README's Install names the real tag; refuses if the release isn't there
git commit -am "docs(readme): install vX.Y.Z [skip ci]" && git push   # direct, as an admin
# at the first stable tag: run the two lines above BEFORE flipping enforce_admins (Mainline protection);
# after the flip, the README commit goes through a PR without [skip ci], because a
# skipped required check never reports and the PR would wait forever
#+end_src

* Changing the contract or the tooling

Plan every change to the record format, the stable words or the tooling
in this order. Each step is done before the next one starts:

1. *Issue.* Open one on this repository: what changes, why, the bump it
   needs (see the table above), and a reproducer or example record.
2. *Schema.* Edit =contract/stacks-log.schema.json=. Bump =x-version= only
   when a change renames or retypes something.
3. *Prose.* Edit =contract/stacks-log.org=, and add a row to its change log.
4. *Producer.* Edit =env/inspect.fs=.
5. *Consumers.* The checks in this repo (=test/= goldens, =pbt/=), and the
   known downstream readers, which are told in step 7.
6. *Checks.* =gmake verify= is green, and a new test covers the change.
   Its planted fault (old producer against new schema, or the reverse)
   goes red.
7. *Notify.* Comment on the issue with the commit, and close it once the
   release ships, as described under downstream deviations.

* Downstream deviations

A downstream project may carry a local patch to its copy of a release when
a fix it needs has not shipped yet. The issue comes first: every deviation
is an open issue on this repository that carries a reproducer, and the
downstream records it as a row (issue, file, change, why now) in its own
=DEVIATIONS.org=.

When a release ships, the downstream project takes these steps:

1. Download the release and verify =SHA256SUMS=.
2. Run each deviation's reproducer against the released files.
3. Drop the rows that the release's =Fixed:= line names and that the
   reproducer confirms.
4. Reopen the issue for any deviation the release claims to fix but does
   not, and keep that row.

On this side, then: a fix is not closed until its reproducer passes against
the release assets, and not merely against =main=. An issue that still has
a downstream deviation open on it gets the label =downstream-patch=, so the
next release can see what is waiting on it.

Making the repository public is the owner's decision. Before anyone makes
it, the history of every branch that will be pushed has to pass the privacy
scan, not just the current tree.
