#+TITLE: Inspecting a running gforth 0.7.3: lldb and in-image tooling
#+DATE: 2026-11-21

Every claim below has the command that checks it and an excerpt of its output.
The full transcripts are in [[file:log/]], regenerated by =lldb/check.sh=. Heap
addresses change from run to run (ASLR plus malloc), so compare structure, not
hex.

Environment: macOS 15 (Darwin 24.1) arm64, Homebrew gforth 0.7.3_3
(=gforth-0.7.3=, =gforth-fast-0.7.3=, =gforth-itc-0.7.3=, built with
Apple clang 16, no DWARF), =/usr/bin/lldb= lldb-1600. The C sources are
in =vendor/gforth-0.7.3= (gitignored), fetched from ftp.gnu.org (sha256
=2f62f2233bf022c23d01c920b1556aa13eab168e3236b13352ac5e9f18542bb0=).

* Quick start

#+begin_src sh
# exact stacks at a Forth-side breakpoint, all three engines
lldb/demo.sh gforth          # or gforth-fast, gforth-itc
# by hand:
lldb -o 'command script import lldb/gforth.py' -o fbrk -o run \
     -- gforth env/brk.fs test/demo.fs
(lldb) fstacks | fbt | fip 1 | finput | fregs | fsee middle | fword +
# attach to a gforth that is already running (here: parked in MS)
lldb/attach.sh gforth
# no debugger: all stacks from inside gforth
gforth env/inspect.fs test/demo-env.fs -e bye
printf '%20s' | gforth env/inspect.fs test/dbg-demo.fs   # dbg+ stepping
#+end_src

* Answers

** Q1. lldb and the VM registers

| state              | gforth                  | gforth-itc              | gforth-fast              |
|--------------------+-------------------------+-------------------------+--------------------------|
| sp, fp             | registers, no fixed binding; exact at =brk= | same      | same, TOS and FTOS cached in registers |
| rp                 | C global =rp= (exact)   | C global =rp= (exact)   | register; exact at =brk= |
| ip                 | C global =saved_ip= (exact) | =saved_ip= (exact)  | register / spill slot; heuristic |
| stack bounds       | =gforth_header= + =dsize= etc. (exact) | same     | same                     |
| names (ip, rstack) | dictionary scan (exact for words with headers) | same | same              |

- Attach and launch both work /outside/ the Claude Code sandbox. Inside it, lldb
  fails with =error: process exited with status -1 (attach failed (attached to
  process, but could not pause execution; attach failed))=. That is the
  sandbox's task_for_pid restriction, not SIP or code signing: =csrutil status=
  says enabled and =DevToolsSecurity -status= says disabled, yet the same
  command works unsandboxed. The binaries are signed ad hoc without the hardened
  runtime (=codesign -dvv= prints =flags=0x2(adhoc)=).
- The Homebrew engine has no debug info. =frame variable= has nothing to show,
  but the useful C globals survive in the symbol table: =gforth_header=
  (ImageHeader*), =gforth_SP/FP/RP/LP/UP=, =vm_prims=, =prim_names= (not in
  itc), =dsize/fsize/rsize/lsize=, and in the =GFORTH_DEBUGGING= engines
  (gforth, gforth-itc, per =engine/Makefile.in=) also =saved_ip= and =rp=.
- There is no =arch/aarch64= in 0.7.3, so =machine=generic=. No VM register is
  pinned to a hardware register (no =SPREG= and so on), and clang allocates them
  separately in each region of the 40 KB =gforth_engine=. Evidence follows.
  - gforth stopped at the =ms= call site (frame 1 of =gforth_ms=):
    =ldr x0, [x28], #0x8 ; bl gforth_ms= and then =mov x25, x28=. sp is in x28
    here and in x25 just before. In gforth-itc at the same point, the
    candidates are x24 and x27 (=log/attach-gforth-itc.txt=).
  - gforth-fast at the first instruction of =f*=: the VM state is reloaded from
    C stack spill slots, so the registers you see on entry are stale:
    #+begin_example
    ->  0x10000ddc8: mov x16, x22
        0x10000ddcc: ldp x24, x26, [sp, #0x28]
        0x10000ddd8: ldp x19, x8, [sp, #0x38]     ; x8 = ip, from the C stack
        0x10000dddc: ldr d0, [x11, #0x8]!          ; second float
        0x10000ddf8: fmul d8, d8, d0               ; d8 = float TOS
    #+end_example
    (=lldb ... -o 'fbreak-prim f*' -o continue -o 'disassemble -s $pc -c 14'=)
- *Exact path: =brk=.* The =call-c= primitive stores the VM registers into
  =gforth_SP/FP/RP/LP= just before it calls a C function (see =prim=, line
  1778). =env/brk.fs= gets =getpid= with =open-lib=/=lib-sym= and defines
  =: brk brk-getpid call-c ;=. =fbrk= puts a breakpoint on getpid, and a
  callback discards hits whose caller is not =gforth_engine=. This gives exact
  stacks in all three engines, including gforth-fast's cached TOS and FTOS,
  because call-c flushes them (=IF_fpTOS(fp[0]=fpTOS)=):
  #+begin_example
  $ lldb/demo.sh gforth-fast            # log/brk-gforth-fast.txt
  engine: gforth-fast (direct threaded, stack caching)  [exact: stopped in brk (CALL-C)]
  brk called from: inner+112
  current: brk+32 executing [ip-1]=call-c, next [ip]=;s
  data stack (bottom first):
    <5> 11 22 33 0 0
  float stack (bottom first):
    <1> 3.25
  return stack:
    [ 0] 0x000000015d842458        inner+112
    [ 1] 0x000000015d8424d0        middle+88
    [ 2] 0x0000000000000000 0          <- loop index
    [ 3] 0x0000000000000004 4          <- loop limit
    [ 4] 0x000000015d842620        outer+144
    [ 5] ...                       interpret1+144
    [ 7] 0x000000015c015118        (-> return stack, 29 cells below top)   <- catch frame
  #+end_example
  The second =continue= gives =<5> 11 22 33 1 20= with index =2=: the =if=
  branch was taken at i=2. gforth and gforth-itc print the same stacks
  (=log/brk-*.txt=).
- *Arbitrary stop, heuristic path* (=fbreak-prim NAME=, Ctrl-C, attach). The
  script unwinds to the =gforth_engine= frame and sorts its registers by the
  stack region they point into, using bounds from =gforth_header=. For ip it
  takes the candidate whose =cell[ip-1]= decodes to the primitive containing pc.
  It also searches the frame's C spill slots, which is what fixes gforth-fast.
  =fregs= reports where each value came from.
  - =lldb/prim-break.sh gforth= (stop on =f*= in =fmix=): =<4> 11 22 33 24=,
    float =<3> 3.25 24 1.5=, =fmix+72 executing f*=. Correct in gforth and itc.
  - gforth-fast, same stop: data correct, float =<3> 3.25 24 0= plus
    =top float is cached in d8 = 1.5=. The memory slot under the cached FTOS is
    stale. d8 is this build's choice; the =fmul d8, d8, d0= above is the
    evidence.
  - =lldb/attach.sh= (=lldb -p= on a gforth sleeping in =ms=, three C frames
    deep: =__semwait_signal= < =nanosleep= < =gforth_ms= < =gforth_engine=):
    gforth gives =<3> 11 22 33=, =<2> 1.5 2.5=, =deep+176 executing ms=.
    Correct.
  - *Fails, with evidence*: gforth-itc in the same attach state picks x24 and
    shows =<1> 11=. It also prints =other sp candidates: x27=0x15300d7e8 (depth
    3) -- rerun as fstacks sp=REG=, and =fstacks sp=x27= gives the right
    =<3> 11 22 33=. In gforth-fast the data TOS is cached, so the top slot is
    garbage: =<4> 11 22 33 4362866024=, and float =<2> 1.5 0= with
    =d8 = 2.5=. These failures are the reason for =brk=. With no fixed
    register binding and no DWARF, nothing exact exists at an arbitrary pc in
    -O2 code.
- *Debug builds*, under =vendor/build-g= and =vendor/build-O0=. Configuring
  needs a newer =config.sub/config.guess= (copied from automake 1.17) because
  0.7.3's config.sub rejects =aarch64-apple-darwin=.
  - =-g -O2=: at =f*=, =frame variable sp fp ip lp= gives
    =<variable not available>= for all four. At the =brk= frame only =sp= is
    available. DWARF adds almost nothing at -O2 (=log/build-g.txt=), so the
    script keeps using its heuristics there.
  - =-g -O0=: every variable is available
    (=sp = 0x...d7e0, fp = 0x...19e8, ip = 0x...2828=, =p fp[0]= gives =1.5=).
    =fstacks= detects this and reports =[debug info (DWARF)]= with exact
    stacks at any stop (=log/build-O0.txt=). Register heuristics would be
    *wrong* at -O0, because the registers hold temporaries, so DWARF takes
    precedence whenever it is available.
- *Names.* =gforth.py= scans the dictionary, =[forthstart, forthstart+dict_size)=
  where forthstart is the =gforth_header= address, for 0.7.3 headers: link
  cell, then a count cell (top 3 bits are the alias/immediate/restrict flags,
  len 1..64), then the name, aligned, then the xt. A candidate is kept only if
  its link is 0 or points to another candidate. This finds 2058 headers after
  loading the demo. An IP or return address maps to =word+offset=. Headerless
  colon code (=:noname=, the code =handler-intro,= builds for =catch=) shows
  as =(noname@ADDR)+off=, found by scanning back for a docol code field.
  Primitives are named from =prim_names[]= where it exists. In every engine,
  the image's primitive headers are aliases whose code field holds the C-side
  xt, and dereferencing that gives the label. That is how gforth-itc, which has
  no =prim_names=, gets names.
- =fip N= and =fsee NAME= decompile threaded code from memory, with inline
  operands (=lit=, =call=, branch targets) taken from the =#= arguments in
  =prim=:
  #+begin_example
  (lldb) fip 2                         # log/brk-gforth-itc.txt
  : middle   (xt=0x144042478, code field (docol))
     0x144042488  +16   lit
     0x144042490  +24     0
     0x144042498  +32   swap
     0x1440424a0  +40   lit
     0x1440424a8  +48     0
     0x1440424b0  +56   (do)
     0x1440424b8  +64   r@
     0x1440424c0  +72   call
     0x1440424c8  +80     (inner)
  -> 0x1440424d0  +88   +
     0x1440424d8  +96   (loop)
     0x1440424e0  +104    -> middle+64
  #+end_example
- *Input stream.* =finput= reads the user variable =current-input= (=gforth_UP=
  plus the offset stored in its body). In 0.7.3 that points to an input record:
  =>in= at +1 cell, =#tib= at +4, =loadline= at +7, =loadfilename= (u, addr) at
  +11/+12, and the line buffer inline at +13 (see =kernel/input.fs=):
  #+begin_example
  input: file-input+16  file=test/demo.fs line=7  >in=6 #tib=19
    outer . f. . . . cr
          ^
  #+end_example
  For =evaluate= input the buffer slot holds a pointer instead. That case is
  detected by the method-table name but has not been exercised.

** Q2. From inside the image (=env/inspect.fs=)

- =~~~= works like =~~= (file:line on stderr) and adds the current word's name,
  =.s=, =f.s=, the return stack *as it was at the =~~~=* (it compiles =rp@=
  inline), and the input line with a caret:
  #+begin_example
  $ gforth env/inspect.fs test/demo-env.fs -e bye          # log/env-gforth.txt
  test/demo-env.fs:3 in inner
  data   <5> 11 22 33 0 0
  float  <1> 3.250000000000E0
  return <R:44> top first
    $14B843F98 = middle +88
    $0 = 0
    $4 = 4
    $14B844110 = outer +144
    ...
  input  test/demo-env.fs:8 >in=6
  outer . f. . . . cr
        ^
  #+end_example
  The output is the same in gforth, gforth-fast and gforth-itc. In the image,
  return addresses are named by scanning back for a =docol:= code field whose
  header gives =name>int= equal to it. Catch frames therefore show as
  =handler-intro, +616=, the nearest real header, whereas lldb identifies the
  headerless code. =(stack pointer)= marks the saved sp/fp/rp/lp in catch
  frames.
- =all-~~= sets the existing hook =printdebugdata= (a =defer= in debugs.fs) so
  that plain =~~= prints all stacks. On top it shows =~~='s own printer frames
  (=outfile-execute=, =.debugline-stderr=, and so on) (=test/tilde.fs=).
- =.cs= (immediate) decodes the compile-time control-flow stack. In 0.7.3 that
  is 3 cells per item (locals-list, address, type) on the data stack, with a
  single-cell colon-sys (=defstart= = 0) underneath (see =kernel/cond.fs=):
  #+begin_example
  : cs-demo  0 ?do  i 2 > if  [ .cs ] begin  [ .cs ] dup while repeat then  loop ;
  CS: here=$127044138
    orig (live) $127044130  (1 cells back)
    do-dest $127044108  (6 cells back) | colon-sys
  CS: here=$127044138
    dest $127044138  (0 cells back)
    orig (live) $127044130  (1 cells back)
    do-dest $127044108  (6 cells back) | colon-sys
  #+end_example
- *dbg.* Stock 0.7.3 =dbg= is *broken in gforth and gforth-fast* on this
  machine. The first step dies with =Address alignment exception=
  (=log/dbg-stock-gforth.txt=). debug.fs says =\ !!! dependency: ITC=: =set-bp=
  stores BREAKER's /xt/ into one threaded-code cell, but in the direct-threaded
  engines a threaded-code cell is a code address. It works in gforth-itc.
  =dbg-fix= patches =set-bp= and =restore-bp= in place: their bodies get
  =call <new> ;s=, and the new versions plant the two-cell =call breaker2=
  sequence (copied from a compiled template). They save both cells of both
  breakpoints before writing, so the loop/branch case with two breakpoints also
  works. =dbg+= adds =dbg-fix= and replaces dbg's =d.s= (depth and top 4 cells)
  with =D: .s F: f.s R: depth + word names=:
  #+begin_example
  $ printf '%20s' | gforth-fast env/inspect.fs test/dbg-demo.fs   # log/dbgplus-gforth-fast.txt
  D: <1> 9  F: <1> 2.500000000000E0 R: 43 cells: (_debug)  (debug)  dbg  interpret1 ...
  ...F: <2> 2.500000000000E0 2.000000000000E0 ...
  1598445F0 104C8DDC8 f*             ->
  D: <1> 9  F: <1> 5.000000000000E0 ...
  #+end_example
  =test/dbg-loop.fs= steps a =do ... loop= with an =if= correctly in gforth
  and gforth-fast after =dbg-fix=. One pitfall: interpretive =compile,=
  followed by restoring =dp= breaks the *next* definition in the
  direct-threaded engines (it ends up "Undefined"), but not in itc. That is why
  the call template is taken from a real colon definition.

** Q3. gforth vs gforth-fast vs gforth-itc

- *gforth* (direct threaded, =GFORTH_DEBUGGING=, no stack caching): the most
  inspectable from outside. =saved_ip= and =rp= are exact at every stop. sp/fp
  come from heuristics that matched the truth in every run here.
- *gforth-itc* (indirect threaded, =GFORTH_DEBUGGING=): same globals, but no
  =prim_names[]=; names come from the image's headers instead. Threaded code
  holds xts, not labels. Its stock =dbg= is the only one that works. The sp
  heuristic chose the wrong register once (above).
- *gforth-fast* (direct threaded, stack caching, superinstructions: 377 entries
  in =prim_names= vs 334): no =saved_ip= and no =rp= global. TOS and FTOS
  (d8) live in registers, and VM registers are reloaded from C spill slots at
  primitive entry. At an arbitrary stop the memory stacks are short by the
  cached top items. Use =brk=: CALL-C flushes everything and the result is
  exact.
- In all three, the stack bounds (=gforth_header=), the dictionary, the input
  record and the Forth-side =sp0/fp0/rp0= user variables are identical and
  exact. Forth's =sp0= is =C top - 8 cells= in gforth-fast and =fp0= is one
  float lower (=gforth_go=: =sp0 -= 8; fp0--=, which makes room for the cache),
  so depths are measured from the Forth user variables, not from the C sizes.
- Also seen: =--debug= shows every =mmap= failing with =Permission denied=
  (stacks and dictionary fall back to =malloc=, so there are no guard pages),
  and =--no-dynamic= is the default (=NO_DYNAMIC_DEFAULT=, generic arch with no
  FLUSH_ICACHE). Threaded code therefore points straight at engine labels, and
  that is what makes =fbreak-prim= work.

* Not done / limits

- The return-stack view does not know which cells are loop parameters or catch
  frames. It marks numbers and stack pointers and leaves the rest to the
  reader.
- There is no TOS-register recovery for gforth-fast's *data* stack at
  arbitrary stops. Which register holds it depends on the pc.
- The =evaluate= input branch of =finput= is untested.
- The dictionary scan is a heuristic. A string literal could look like a
  header with a valid link, but none was seen.
